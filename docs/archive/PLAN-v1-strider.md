# School Pickup — Staged Learning Plan

A practice project that covers the stack from the Strider *Full-stack Engineer (React, TypeScript, Python)* posting.
The product: schools, families and staff coordinating **student pickup** — who picks up whom, from where, and when.

**Rule of the project:** you write the core code. Claude reviews, explains, quizzes and writes only boilerplate.
Every stage ends with something running that you can demo, plus a short ADR in `docs/adr/`.

---

## Target stack

| Area | Tech |
|---|---|
| Backend | Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), Alembic, `uv` |
| DB | PostgreSQL 16 + PostGIS |
| Frontend | TypeScript, React, TanStack Start (SSR), TanStack Router + Query, Mantine, Zod |
| API contract | OpenAPI (generated by FastAPI) → typed TS client (`openapi-typescript` + `openapi-fetch`) |
| Auth | Keycloak, OpenID Connect (Auth Code + PKCE), JWT validation in FastAPI |
| Maps | PostGIS, GeoAlchemy2, Leaflet (`react-leaflet`) |
| Tests | pytest + pytest-asyncio + httpx, Vitest + Testing Library, (Playwright stretch) |
| Infra | Docker + Docker Compose, GitHub Actions; stretch: gRPC, Helm/K8s |

## Monorepo layout

```
school-pickup/
  apps/
    api/          # FastAPI service
    web/          # TanStack Start app
  packages/
    api-client/   # generated TS client from OpenAPI
  infra/
    docker-compose.yml
    keycloak/     # realm export
  docs/adr/
  .github/workflows/
```

## Stage 0 — Skeleton & local infra (½ day)

**Build**
- Monorepo folders, `pnpm` workspace for TS, `uv` project for Python.
- `docker-compose.yml` with `postgis/postgis:16` and a healthcheck.
- FastAPI app with `GET /health` that checks the DB connection.
- ADR-001: "Monorepo with Python API + TS web".

**Learn / be able to explain**
- What Docker Compose healthchecks and `depends_on: condition: service_healthy` do.
- Why `uv` / lockfiles; why a monorepo.

**Done when:** `docker compose up` and `curl localhost:8000/health` → `{"db": "ok"}`.

## Stage 1 — Data model & REST API (2–3 days)

**Domain:** `School`, `Student`, `Guardian`, `StudentGuardian` (many-to-many, with `can_pickup: bool`), `PickupEvent`.

**Build**
- SQLAlchemy 2.0 models using `Mapped[...]` / `mapped_column`, async engine + `async_sessionmaker`.
- Alembic migrations (autogenerate, then read and fix them by hand).
- Pydantic v2 schemas: separate `Create`, `Update`, `Read` models.
- CRUD routers with pagination, filtering, proper status codes (201, 204, 404, 409, 422).
- Dependency injection: `get_session` via `Depends`.
- pytest: async test client (`httpx.AsyncClient` + `ASGITransport`), a test DB, one transaction per test that is rolled back.

**Learn / be able to explain**
- Async SQLAlchemy pitfalls: lazy loading in async (`MissingGreenlet`), `selectinload` vs `joinedload`, N+1.
- Transactions: when to commit; what happens to a unique violation; mapping `IntegrityError` → 409.
- Indexes: which columns you indexed and why. Run `EXPLAIN ANALYZE` on one query.
- Pydantic v2: `model_config = ConfigDict(from_attributes=True)`, validators, `Field` constraints.

**Challenge:** `POST /pickup-events` must reject a guardian without `can_pickup` — enforced in the service layer **and** covered by a test.

**Done when:** `/docs` shows a clean API; `pytest` is green; migrations go up and down cleanly.

## Stage 2 — Frontend foundation + typed client (2–3 days)

**Build**
- TanStack Start app with Mantine (theme, AppShell layout, dark mode).
- Generate `packages/api-client` from `/openapi.json`; add a `pnpm gen:api` script.
- Routes: `/schools`, `/schools/$schoolId`, `/students/$studentId`.
- Data fetching: TanStack Query with route loaders (`ensureQueryData`) so pages render on the server (SSR).
- Loading / error / empty states.

**Learn / be able to explain**
- SSR vs CSR vs hydration; what a loader does in TanStack Start, and how it compares to Next.js App Router server components.
- Query keys, `staleTime` vs `gcTime`, invalidation after a mutation, optimistic updates.
- Why a contract-first typed client beats hand-written `fetch` types.

**Challenge:** change a field name in the API → regenerate the client → the TS compiler shows you every place that broke. Fix them.

**Done when:** pages render with data on first load (check view-source), with no `any` types.

## Stage 3 — Forms, validation, accessibility, FE tests (2 days)

**Build**
- Create/edit forms for Student and Guardian (Mantine Form + Zod), with server errors (422) mapped onto fields.
- Pick one screen and recreate it from a Figma community UI kit (practice for the "Figma → UI" requirement).
- Responsive layout (mobile-first), keyboard navigation, labels, focus management in modals.
- Vitest + Testing Library: form validation, submit success, server error display. Mock the API with MSW.

**Learn / be able to explain**
- Controlled vs uncontrolled inputs; when re-renders happen; `useMemo`/`useCallback` only when measured.
- Accessibility basics: roles, `aria-*`, color contrast, testing with `getByRole`.
- Building a small reusable component library (`<DataTable>`, `<ConfirmDialog>`).

**Done when:** you can fill out a form using only the keyboard, and the tests are green.

## Stage 4 — Auth with Keycloak / OIDC (2–3 days)

**Build**
- Keycloak in Compose; a realm with clients `web` (public, PKCE) and `api` (bearer-only); roles `guardian`, `staff`, `admin`. Commit the realm export.
- Web: Authorization Code + PKCE login, token refresh, logout, protected routes.
- API: validate JWTs using JWKS (cache the keys), check `aud`/`iss`/`exp`; a `current_user` dependency; role guards.
- Link Keycloak `sub` → `Guardian` / staff rows.

**Learn / be able to explain**
- OAuth 2.0 vs OIDC; ID token vs access token vs refresh token; why PKCE.
- Where to store tokens in the browser (memory vs cookies vs localStorage) and the XSS/CSRF trade-offs.
- 401 vs 403.

**Challenge:** a guardian can only see their own students. Write the test **before** the code.

**Done when:** three demo users (guardian, staff, admin) see different data.

---

## Stage 5 — Multi-tenancy & fine-grained authorization (2 days)

**Build**
- Every school is a tenant: `school_id` on the tenant-owned tables, tenant resolved from the token claim.
- Enforce scoping in one place (a repository/session helper), not in every query by hand.
- Optional: Postgres Row-Level Security as a second layer.
- Authorization rules as a separate module: "staff of school X can mark pickup for students of school X", "guardian can pickup only if `can_pickup`".
- ADR: "Tenant isolation strategy".

**Learn / be able to explain**
- Shared schema vs schema-per-tenant vs database-per-tenant.
- RBAC vs ReBAC; what SpiceDB / Zanzibar solve (stretch: model the rules as a SpiceDB schema).
- Handling PII: logging hygiene, which fields are sensitive (FERPA mindset).

**Challenge:** write a test that tries to read another tenant's student by ID → must return 404 (not 403 — explain why).

---

## Stage 6 — Geospatial: pickup points & map (2 days)

**Build**
- PostGIS `geography(Point)` for school pickup points and guardian home locations (fake data); GeoAlchemy2.
- `GET /pickup-points/nearest?lat&lng` using `ST_DWithin` / `ST_Distance` with a GiST index.
- React-Leaflet map: pickup points, a guardian's location, click to pick a point. Render on the client only (Leaflet needs `window` — handle it under SSR).

**Learn / be able to explain**
- geometry vs geography, SRID 4326, why GiST.
- Dealing with browser-only libraries in an SSR app.

**Done when:** the map shows the 3 nearest pickup points to a chosen location.

## Stage 7 — CI, quality & performance (1–2 days)

**Build**
- GitHub Actions: lint (ruff, eslint), type-check (mypy/pyright, `tsc`), pytest with a Postgres service container, Vitest, build the Docker images. Cache dependencies.
- Production-style Dockerfiles (multi-stage, non-root user).
- A check that fails CI if the generated API client is out of date.
- Front-end performance: route code-splitting, a bundle analysis, the React Profiler on one slow list (then fix it).

**Done when:** a PR shows green checks, and you can explain each job.

## Stage 8 — Stretch goals (pick any)

- **gRPC:** a small `notifications` service (Python, `grpcio` + protobuf); the API calls it when a pickup is marked. Explain when gRPC beats REST.
- **Realtime:** staff dashboard with live pickup status (SSE or WebSockets).
- **E2E:** Playwright covering login → mark pickup.
- **K8s:** Helm chart + kind cluster; read about Argo CD / GitOps.
- **AI feature:** "Summarize today's pickups" using the Claude API, reviewed critically like any other code.

## How to work with Claude on this (VS Code)

1. Start each stage with: *"We're on Stage N of PLAN.md. Quiz me on the 'Learn' items first, then give me the first task without the solution."*
2. Write the code yourself. Then: *"Review my diff like a senior reviewer at a startup — correctness, security, tests."*
3. Ask for boilerplate only (Compose files, the Keycloak realm, config) — and read every line it writes.
4. End each stage with: *"Give me 5 interview questions on what I just built,"* answer them out loud in English (C1 is required), and write the ADR.
5. Keep a `LEARNINGS.md` with your mistakes and fixes — it's great material for interview stories.

**Rough total:** ~3 weeks part-time for Stages 0–7.
